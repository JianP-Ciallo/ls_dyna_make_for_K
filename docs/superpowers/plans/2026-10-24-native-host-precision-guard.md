# Python 宿主高精度保护修复方案（待执行）

本轮仅完成最小诊断及中间产物清理，本文件是后续修复方案，**尚未修改或安装数值修复**。

## 已闭合的原因

同一个新失败检查点，在同一 CPython 进程、同一线程、同一材料构建对象下，仅改变 x87 精度控制位：53 位返回 -1；64 位返回 0，真实 σ33=+1.2252512372745716e-12 Pa；恢复 53 位后再次返回 -1。失败 root 字段与整栋现场逐字段完全相同。

当前 `supportsPrecise33()` 的编译期 digits>53 检查没有保证运行时有效精度。Python 初始 CW=0x27f，独立 MinGW EXE 为0x37f；volatile `(1+2^-60)-1` 在前者为0，后者为2^-60。此前独立 EXE 的精度验收遗漏了这个宿主边界。旧检查点在53位也恰好过门槛（σ33≈1.8626e-9），因此只扩充旧点不能保证覆盖新失败。

## 推荐实现

1. 新增局部、可嵌套的扩展精度 RAII 保护。进入数值计算时保存当前线程完整 x87 控制字，仅把 precision-control 置为64位，读回核实；返回、错误和异常路径均恢复来时控制字。保留调用者的舍入方式、异常掩码等其他控制位，不改 MXCSR 控制位，也不在 Python 启动时永久更改全局环境。
2. 保护范围覆盖 PlateFiber 根搜索、三维隐式精度求值，以及在调用精度 setter 前会组合高低位的入口（如 ASD 增量/高低位读取）。不能只在三维 setter 内保护，而让 Plate 根算术仍在53位执行；也不能先把 ε33 算成53位再进入保护。
3. `supportsPrecise33` 与实际能力闭合：对于已验证的 x86/MinGW 路径，由保护保证64位；若读回或有效位自检不满足，不冒称高精度可用，应保存明确诊断并按原规则失败。其他平台保留明确能力边界。
4. 诊断补充 `use_precise`、编译 digits、进入/有效 CW、厚度及括区高低位。避免只记录转为 double 的根坐标，导致无法判断实际精度。σ33 仍直接读取活三维材料返回值，绝对门槛保持1e-8 Pa，不插值、不置零、不修改模型输入。
5. 验证优化后的实际构建：通过明确的编译/调用边界避免浮点运算被常量折叠或移到保护范围外，使用运行期有效位探针和材料结果共同确认，不能只在调试版读到64位就认定修复完成。

## 轻量 RED→GREEN 验收

- 固定本轮新检查点及旧检查点，在 CPython 同进程恢复单材料。先确认默认53位下新点失败，再验证修复后默认53位和来时64位均通过，并保持五维外部应变完全相同。
- 每次调用前后核对来时 CW 恢复；包含成功、材料拒绝、异常、回退、嵌套和不同线程。核对其他 CW/MXCSR 控制位未被篡改，不以设置整个进程64位替代局部保护。
- 核对真实 |σ33|≤1e-8、复制/提交/序列化/后续路径、凝聚切线及原始材料历史；宿主内桥接仅用 char*/int/double 传递 JSON，禁止把 MinGW long double 直接跨 Microsoft ctypes ABI。
- 保留独立 EXE 回归，但增加 Python 宿主内材料验收，不能再把启动 EXE 的测试当作 pyd 宿主路径验证；继续做实际 pyd 的最小板片及相关轻量专项。
- 构建另一个独立运行时，保留现有运行时和历史结果；不在本方案内启动整栋、13 单元、TNT、全量或其他重型测试。
