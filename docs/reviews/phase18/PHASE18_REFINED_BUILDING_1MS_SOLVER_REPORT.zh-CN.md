## 找到并修复的问题

1. 直接执行生成脚本时没有建立仓库导入路径，导致模块导入失败；脚本现从自身位置确定仓库根。
2. R12 逗号字段要求最多 10 个字符，最初弹性模量以长整数输出并触发 `Error 10459`；现使用受限有效数字格式并有自动测试。
3. 资产清单包含只读 `mappingproxy`，初次 JSON 写入失败；现递归转换为普通 JSON 值。
4. 初次商业 mcheck 使用 `memory=8g`，R12 将其解释为 80 亿 words 而非 8 GB，产生内存分配错误；正式运行统一使用 `memory=1g`。
5. 地铁入口初次 1 ms 虽正常结束，但 56 个 `pavilion_glazing` 壳单元触发 `Warning 21129`，最差形状指标约 0.017。根因是玻璃下边缘追随楼梯锯齿面，而上边缘为连续屋面。生成链路现改用连续坡向玻璃基座，并为整条玻璃带选择统一的 7 层竖向划分；相邻玻璃面共享节点、无悬挂边，全部壳单元指标不低于 0.1，mcheck 和 1 ms 日志均不再出现该警告。
6. 首轮自动验收把缺失的沙漏能量序列当作 0，且只检查“正常终止”，未证明实际问题时间达到 1 ms。K 包现显式写入 `*CONTROL_ENERGY`（`HGEN=2`），结果解析器要求真实沙漏能量序列，并同时要求显式终止标志和 `final_problem_time_s >= 0.001`；缺失任一证据即失败。
7. 首轮地铁玻璃按单块分别选择竖向层数，虽然单元质量合格，但相邻分块可能形成悬挂节点。现改为整条玻璃带统一层数，并加入边共享计数回归测试。

旧运行均可追溯保存在根目录 `diagnostics` 下，其中包括 `03_subway_entrance_pre_glazing_mesh_fix` 和 `pre_control_energy_and_conforming_glazing_fix`；最终 `models` 目录只包含本报告列出的三套修正版模型与对应求解证据。

## 适用边界

本报告证明的是 K 关键字闭合、拓扑可初始化及 1 ms 短时数值稳定性。模型使用诊断用线弹性代理材料、固定全局最低节点和重力载荷，没有施加爆炸载荷，也没有完成非线性材料、接触/耦合、地基、网格收敛或全时程校准。

因此三套模型可以进入下一阶段真实求解配置与工程复核，但不能据此宣称爆炸响应工程有效。所有产物继续保持：

- `solver_ready=false`
- `requires_project_review=true`
- `engineering_validated=false`
